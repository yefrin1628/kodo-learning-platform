# Kodo API — contrato (v1, en construcción)

Qué endpoint consume cada parte del frontend. Se actualiza en cada bloque que conectemos — no es spec completa de antemano, es el mapa real de lo que ya existe.

Base URL (dev): `http://localhost:4000`. Base URL (producción): `https://kodo-learning-platform-api.vercel.app` — desplegada como función serverless de Vercel (ver bloque "Vercel serverless" más abajo), con Postgres real en Neon. Todos los endpoints marcados 🔒 requieren `Authorization: Bearer <accessToken>`.

Frontend en producción: `https://koda.school` (dominio propio, DNS vía Hostinger apuntando a Vercel) / `https://kodo-learning-platform.vercel.app` como alias.

## Auth — `apps/api/src/auth`

| Endpoint | Consume en frontend | Notas |
|---|---|---|
| `POST /auth/register` | `doRegister()` (vista `vAuth`, modo registro) | Body: `{email,password,displayName,username}`. `username` se genera automático desde el nombre (no hay campo visible nuevo), reintenta con sufijo si 409. Devuelve `{user:{id,email,profile},accessToken,refreshToken}`. |
| `POST /auth/login` | `doLogin()` (vista `vAuth`, modo login) | Body: `{email,password}`. Misma forma de respuesta que register. |
| `POST /auth/refresh` | `bootAuth()` al cargar la página | Body: `{refreshToken}`. Rota el refresh token — el nuevo reemplaza al viejo en `localStorage`. |
| `POST /auth/logout` | `doLogout()` | Body: `{refreshToken}`. Revoca el token en servidor. |
| `GET /me` 🔒 | `bootAuth()`, `doLogin()`, `doRegister()`, `go('profile')` → `syncUserFromServer()` | Devuelve `{id,email,userProfile,userStats,streak,courseProgress,lessonProgress,xpToday,xpWeek,exercisesAnswered,exercisesToday,accuracy,achievements,challengesClaimedToday}`. `courseProgress`/`lessonProgress` (solo lecciones `completed:true`, con `lesson.key`) son lo que `syncUserFromServer()` usa para reconstruir `U.done` por completo — así `isUnlocked()`/`coursePct()`/`getNext()` ven el progreso real en cualquier dispositivo, no solo en el navegador donde se completó; también se usa para reconstruir `U.day.lessons`/`U.day.perfect` (lecciones/perfectas de hoy). `xpToday`/`xpWeek`/`exercisesToday` son sumas/conteos en vivo (mismo criterio que `ranking.service.ts` y `challenges.service.ts`'s `measure()`), nunca un contador que el cliente incremente por su cuenta. `exercisesAnswered`/`accuracy` vienen de un `aggregate` sobre `ExerciseProgress` (histórico, no solo hoy). `achievements` solo trae `achievement.key` por cada `UserAchievement`; `challengesClaimedToday` solo la `challenge.key` de cada `UserChallengeProgress` reclamado hoy — ambos catálogos completos (nombre/icono/descripción) ya viven local (`ACHS`/`CHALLENGES`), seeded del mismo contenido, así que no viajan dos veces. `go('profile')` pide `/me` fresco cada vez que se entra al perfil, no solo en login. |

## Cursos y lecciones — `apps/api/src/courses`, `apps/api/src/lessons`

| Endpoint | Consume en frontend | Notas |
|---|---|---|
| `GET /courses` | `hydrateCoursesFromApi()` (tras register/login/bootAuth) | Lista los 7 cursos publicados con conteo de unidades/lecciones. |
| `GET /courses/:slug` | `hydrateCoursesFromApi()` | Curso + unidades + lecciones (sin ejercicios). Se llama una vez por curso tras `GET /courses`. `adaptApiCourse()` convierte la respuesta a la forma legacy de `COURSES` (mismos ids/keys de siempre). |
| `GET /courses/:slug/lessons` | *(pendiente)* | Lista plana de lecciones de un curso, con su unidad. |
| `GET /lessons/:key` | `hydrateLessonFromApi(key)` (dentro de `openLesson()`) | Lección completa: intro + ejercicios + opciones. `key` es el mismo id que ya usa el frontend (`js-1`, `html-p1`, etc.). `adaptApiLesson()`/`adaptApiExercise()` reconstruyen la forma legacy de `LESSONS[key]` para los 13 tipos de ejercicio; fallback silencioso al contenido local si falla. **No expone la respuesta correcta**: `ExerciseOption.isCorrect` nunca viaja aquí, ni `content.acc`/`ans` (TYPE_ANSWER/TRANSLATE), ni el orden real de `content.w` (ORDER/TRANSLATE comparten el mismo banco de palabras tap-to-build — llega pre-mezclado como `content.bank`, ver hallazgo crítico del audit de seguridad). La respuesta correcta solo se revela después de un intento real, en `POST /learning/exercises/:exerciseId/answer`. |

## Motor de aprendizaje — `apps/api/src/learning`

| Endpoint | Consume en frontend | Notas |
|---|---|---|
| `POST /learning/exercises/:exerciseId/answer` 🔒 | `lsCheck()` / `matchDone()` / `resolveLang()`, vía `answerPayloadFor()` | Body varía por tipo: `selectedIndex` (choice/tf/fill/bug/listen/predict/convo), `text` (type/translate/order), `code` (run), `pairs` (match), `{}` (speak). Solo se llama cuando el ejercicio actual tiene `id` real (viene de `GET /lessons/:key`); si la lección hidrató pero la llamada falla, ya no se evalúa localmente (no hay con qué: la respuesta correcta no vive en el cliente) — se muestra un error de conexión y el ejercicio queda sin responder. El servidor decide correcto/incorrecto, XP y corazones — el cliente nunca envía esos valores. **Exige que la lección esté realmente desbloqueada** (`assertLessonUnlocked()`, misma regla que `completeLesson()`: primera del curso, o la anterior tiene `LessonProgress.completed`) — 403 si no, sin tocar XP/corazones/SRS; `U.done`/`U.pro` del cliente nunca se consultan para esto. Devuelve además `correctIndex`/`correctAnswer` (la respuesta correcta, recién revelada después del intento) para que `lsCheck()` pueda pintar el feedback "Respuesta correcta: X" sin haber tenido la respuesta de antemano. **Ejercicios tipo RUN tienen un kill-switch** (`RUN_EXECUTION_ENABLED`, env var): `run-student-code.ts` ejecuta el código enviado con el módulo `vm` de Node, que no es un sandbox real — con la variable en `false`, cualquier ejercicio RUN (sin importar `content.lang`) devuelve `503` antes de tocar `runStudentCode()`, sin efectos secundarios; el frontend lo distingue de un error de red y no cae al fallback local (que otorgaría XP local sin validación). Ver hallazgo crítico del Production Readiness audit — el Execution Worker aislado es la solución definitiva, esto es la mitigación mientras tanto. |
| `POST /learning/lessons/:key/complete` 🔒 | `lsFinish()` → `applyLessonCompletion()` | Exige haber respondido todos los ejercicios y la lección anterior completada (400/403 si no). Devuelve `{success,lesson,rewards:{xp,gems},stats:{xp,level,streak},courseProgress,achievementsUnlocked,challengesCompleted}`. `U.xp`/`U.streak` se fijan de forma absoluta desde `stats` (nunca se incrementan localmente) — así el bonus de lección jamás puede volver a pagar el XP que ya se pagó por ejercicio individual. Si falla, no se inventa recompensa local: `LS.completeError` se muestra con botón "Reintentar" (`retryCompleteLesson()`). `achievementsUnlocked` (25 condiciones reales en `achievements.service.ts`) ya no se descarta: `applyServerAchievements()` actualiza `U.ach` y encola el modal de celebración (icono/nombre/descripción/XP) por cada logro nuevo. `challengesCompleted` (4 condiciones reales en `challenges.service.ts`) tampoco: `applyServerChallenges()` marca `U.day.claimed` y muestra el mismo toast que el `checkChallenges()` local ya usaba — el servidor decide qué se desbloqueó en ambos casos, el cliente solo lo muestra y nunca vuelve a otorgar el XP/gemas ya incluidos en `rewards`. |
| `POST /learning/hearts/refill` 🔒 | `useGemsHearts()` (modal "Te quedaste sin vidas", botón "Usar 30 gemas") | Sin body: costo (30 gemas) y vidas objetivo (5) son constantes del servidor (`HEARTS_REFILL_COST`/`MAX_HEARTS` en `constants.ts`), el cliente no envía ni influye en ninguno de los dos. Un solo `UPDATE ... WHERE gems >= 30 AND hearts < 5` atómico — sin necesidad de `$transaction`, ya es una sola sentencia — así que un doble clic/petición concurrente nunca cobra dos veces (el perdedor de la carrera simplemente no encuentra fila que actualizar). 400 si faltan gemas, 400 si las vidas ya están llenas, 400 si el usuario es Pro (ya tiene vidas infinitas, el refill no aplica). Devuelve `{gems,hearts}` reales — el cliente ya no resta/asigna nada por su cuenta. |

## Ranking — `apps/api/src/ranking`

| Endpoint | Consume en frontend | Notas |
|---|---|---|
| `GET /ranking?period=weekly\|monthly\|allTime` 🔒 | `go('ranking')`/`setRankingPeriod()` → `loadRanking()` | Default `weekly`. Devuelve `{period,entries:[...],me:{rank,xp}}`. `me` siempre presente aunque esté fuera del top 20 — `vRanking()` renderiza una fila "Tu posición" aparte en ese caso. Se pide fresco cada vez que se entra a la vista y en cada cambio de período; `loadRanking()` descarta la respuesta si el período ya cambió o el usuario salió de la vista, para que una respuesta lenta de un período viejo no pise una más nueva. |

## SRS / Vocabulario — `apps/api/src/vocabulary`

| Endpoint | Consume en frontend | Notas |
|---|---|---|
| `GET /vocabulary/:courseSlug` 🔒 | `hydrateVocabFromApi()` (boot/login/registro sin esperar, y forzado al entrar a `vocab`/`review`) | Catálogo completo de palabras del curso con la reseña real del usuario (`mastery`/`seen`/`mistakes`/`correctAnswers`/`nextReview`, en ceros si nunca se repasó). Reconstruye `U.srs` (solo para palabras con `seen>0`, igual que el filtro que ya usaba `dueList()`) y `U.vocabIds` (para todas, incluidas las nunca vistas) — `dueList()`/`langStats()`/`vVocab()`/`vReview()` no cambiaron nada, solo leen datos reales ahora. |
| `POST /vocabulary/:vocabularyId/review` 🔒 | `lsCheck()`, cuando el ejercicio de repaso trae `vocabularyId` (asignado por `reviewExFrom()`) | Body: `{answer:string}` — el texto de la opción elegida. El servidor compara contra `Vocabulary.translation` (normalizado, ignora acentos/mayúsculas) y decide correcto/mastery/próxima revisión con la misma fórmula que ya usaba `answerExercise()` para LISTEN/MATCH en lecciones reales (`VocabularyService.applyResult()`, compartida, no duplicada). No otorga XP — el repaso sigue ganando XP por el camino local existente, sin cambios en este bloque. |

## Tienda — `apps/api/src/shop`

| Endpoint | Consume en frontend | Notas |
|---|---|---|
| `GET /shop/inventory` 🔒 | `hydrateShopFromApi()` (boot/login/registro sin esperar, forzado al entrar a `Tienda`) | Devuelve `{gems,hearts,items:[{itemKey,equipped,purchasedAt}]}`. No hay `GET /shop` de catálogo aparte: precio/nombre/ícono/descripción son contenido estático que ya vive en `SHOP` (frontend) y en `SHOP_ITEMS` (`shop-items.constants.ts`, backend) — igual que `ACHS`/`CHALLENGES`, solo lo que está desbloqueado/poseído viaja del servidor. `U.items` se reemplaza por completo con la lista real de objetos poseídos; `U.equip` (solo `glasses`/`headphones`/`crown`) se reconstruye del campo `equipped` de cada fila. |
| `POST /shop/:itemKey/purchase` 🔒 | `buy(id)` | Sin body: precio y "kind" (consumible vs. poseíble) siempre salen de `SHOP_ITEMS` en el servidor, nunca del cliente — no hay forma de que el cliente influya en cuánto cuesta algo. Gemas (y, para `hearts`, el chequeo de vidas llenas) se validan y descuentan en un solo `UPDATE ... WHERE gems >= price [AND hearts < 5]` dentro de una transacción, así que una segunda petición concurrente siempre revisa el valor recién confirmado en vez de uno obsoleto. Objetos "poseíbles" (`theme-cyan`, `theme-sunset`, `glasses`, `headphones`, `crown`, `badge`) crean una fila en `UserInventory` con unique `(userId,itemKey)` — doble compra da 409, incluida la variante en carrera (la segunda transacción revierte por completo, incluidas las gemas, gracias al rollback automático de `$transaction`). Los equipables (`glasses`/`headphones`/`crown`) se auto-equipan al comprarlos. Devuelve `{itemKey,gems,hearts}`. |
| `POST /shop/:itemKey/equip` 🔒 | `toggleEquip(k)` (perfil, sección "Colección de Kody") | Body: `{equipped:boolean}`. 404 si el objeto no es equipable, 403 si el usuario no lo posee. Devuelve `{itemKey,equipped}`. |

## Suscripciones / Pro — `apps/api/src/subscriptions`

| Endpoint | Consume en frontend | Notas |
|---|---|---|
| `POST /subscriptions/checkout` 🔒 | `Payments.activate(planId)` | Body: `{planKey:'PRO_MONTHLY'\|'PRO_YEARLY'}`. Activación simulada (mismo texto "MVP, sin cobros reales" que ya existía) pero real server-side: precio/plan salen de la tabla `Plan` (ya sembrada desde el arranque del backend), nunca del cliente. Una fila `Subscription` por usuario (`userId` único) — reactivar/cambiar de plan hace upsert sobre esa misma fila en vez de acumular historial, así que no hay condición de carrera de doble-checkout que duplique filas. Devuelve `{planKey,status,currentPeriodEnd}`. |
| `POST /subscriptions/cancel` 🔒 | `closeProToFree()` | Sin body. Downgrade inmediato (no hay período de gracia, igual que el botón local de antes) — pone `status:'CANCELED'`. 400 si no hay suscripción `ACTIVE`. |

`GET /me` ahora también devuelve `isPro:boolean` y `subscriptions:[{...,plan:{key}}]` (solo la fila `ACTIVE`, si existe) — no hay `GET /subscriptions` aparte, se reutiliza `/me` igual que Shop reutiliza `/shop/inventory` en vez de sumar un endpoint de catálogo. `syncUserFromServer()` fija `U.pro`/`U.proPlan` desde ahí en cada boot/login/checkout/cancel.

Beneficios Pro aplicados **server-side**, no en el cliente: dentro de `POST /learning/exercises/:exerciseId/answer`, `learning.service.ts` consulta `SubscriptionsService.isPro(userId)` y, si es Pro, (a) no descuenta vidas en una respuesta incorrecta en modo lección, y (b) paga el doble de XP en una respuesta correcta. El cliente ya no decide ninguna de las dos cosas.

## Qué controla cada lado

- **Backend (fuente de verdad):** XP, nivel, progreso de curso/lección/ejercicio, corazones, racha, SRS, logros, challenges, ranking.
- **Frontend (experiencia):** animaciones, confeti, sonidos, mascota, transiciones, feedback visual, barras de progreso — todo eso sigue local y no cambia.

- ✅ Carga de lecciones conectada: al abrir una lección, `LESSONS[clave]` se sobrescribe con el contenido real (intro + ejercicios) de `GET /lessons/:key`.
- ✅ Progreso de ejercicios conectado: responder cualquiera de los 13 tipos de ejercicio se valida en `POST /learning/exercises/:exerciseId/answer` — XP, corazones y SRS los decide el servidor. El multiplicador x2 de XP de Pro ya aplica server-side (ver bloque de Suscripciones); el impulso x2 comprado en la Tienda (`boost`) sigue sin efecto sobre respuestas validadas por el servidor — gap ya documentado en el bloque de Tienda, no es parte de este.
- ✅ Completar lección conectada: `POST /learning/lessons/:key/complete` paga el bonus de fin de lección, gemas, racha, XP de módulo/curso y logros/challenges — todo server-side. El núcleo de aprendizaje (cursos → lecciones → ejercicios → completar lección) ya corre realmente contra Postgres, no solo la interfaz.

Corregidos dos bugs reales: login/registro no traían el `/me` completo (un dispositivo nuevo veía todo bloqueado pese al progreso real), y `rollover()` podía resetear la racha localmente incluso después de que el servidor ya hubiera confirmado el valor correcto.
- ✅ Perfil + estadísticas conectado: ejercicios respondidos, precisión, cursos iniciados/completados, logros desbloqueados y actividad reciente en `vProfile()` leen todos de `GET /me` — `U.ach` ya no es estado local, es la lista real de `UserAchievement`. `U.code.xp`/`U.lang.xp`/`U.code.seconds`/`U.lang.seconds`/`U.lang.words` siguen local a propósito (sin agregado server-side de XP por categoría ni de tiempo estudiado; palabras es del bloque SRS/vocabulario).
- ✅ Logros reales conectado: el evento de desbloqueo en vivo (`achievementsUnlocked` de `POST /learning/lessons/:key/complete`) ya dispara el modal de celebración con datos del servidor, no de `checkAch()` local. `checkAch()` sigue activo solo para triggers sin equivalente server-side todavía (correr código en el editor, modo práctica/repaso) — ambos sistemas escriben en el mismo `U.ach`, así que no hay duplicados.
- ✅ Challenges reales conectado: de los 4 challenges del backend, 2 (`ch-lessons3`/`ch-xp100`) ya tenían equivalente local (`ch-l3`/`ch-xp`, distinto key) y ahora dependen de `challengesCompleted`; los otros 2 (`ch-exercises20`, `ch-streak`) no existían en el widget local y se agregaron. `U.day.lessons`/`U.day.perfect`/`U.day.ex` se reconstruyen desde `GET /me` para que las barras de progreso no arranquen en 0 en un dispositivo nuevo.
- ✅ `ch-perf`/`ch-code` server-authoritative (bloque separado, 2º hallazgo del Security & Server Authority Audit): eran los últimos 2 challenges que otorgaban XP local vía `gainXP()` directo, sin validación del servidor — farmeable desde la consola sin ninguna petición de red (confirmado en el audit). Ahora tienen fila real en `Challenge` igual que los otros 4: `lesson_perfect` cuenta `LessonProgress.perfect:true` completadas hoy (el mismo flag que `completeLesson()` ya calculaba a partir de errores reales); `code_run` cuenta `ExerciseProgress` de ejercicios tipo `RUN` respondidos hoy — solo cuentan los de JS/Python, porque los `RUN` en HTML se evalúan 100% en el cliente (sin llamada al servidor, por diseño original: no hay forma de validar renderizado HTML del lado del servidor sin un rediseño mayor, fuera de alcance de este bloque). `checkChallenges()` ya ignoraba `server:true`, así que quitar `apply:()=>gainXP(...)` bastó para cerrar el hueco — no se agregó infraestructura nueva.
- ✅ Ranking frontend conectado: `vRanking()` es 100% `GET /ranking` — sin bots, sin XP simulado por hash local (`BOTS`/`hashStr()` eliminados). Semanal/Mensual/Todo el tiempo, "Tu posición" fuera del top 20, estado de carga y fallback con reintento en fallo de red, todo verificado contra un dataset real de 21 usuarios (incluyendo un empate de XP real).
- ✅ SRS/vocabulario conectado (este bloque): el backend no tenía flujo de repaso independiente (`VocabularyReview` solo se tocaba de pasada al responder LISTEN/MATCH en una lección real) — se agregó `VocabularyModule` (`GET /vocabulary/:courseSlug`, `POST /vocabulary/:vocabularyId/review`) reutilizando/extrayendo la fórmula SRS ya existente en `learning.service.ts`, no una copia. Bug real encontrado y corregido: `markWords()` sumaba doble el mismo repaso en ejercicios `listen` (mismo bug que ya se había corregido en el backend hace varios bloques, nunca se replicó el fix al frontend).
- ✅ Tienda conectada (este bloque): el backend no tenía ningún concepto de tienda/inventario — se agregó la tabla `UserInventory` y `ShopModule` desde cero. Gemas/vidas siguen viviendo en `UserStats` (ya existían); lo nuevo es solo qué se posee y qué está equipado. Dos límites preexistentes se mantienen intactos a propósito (no se "arreglan" en este bloque porque no era su alcance): el objeto `shield` (protector de racha) y `boost` (impulso XP x2) ahora sí descuentan gemas reales de forma atómica, pero su *efecto* de juego sigue sin backend — `shield` no tiene contrapartida en `rollover()` (la racha es 100% server-derivada desde el bloque de Dashboard) y `boost` no aplica ningún multiplicador sobre las respuestas validadas por el servidor — a diferencia del x2 de **Pro**, que sí quedó conectado en el bloque de Suscripciones, este x2 puntual de un solo uso (comprado con gemas) sigue siendo un gap conocido, sin fecha asignada. `theme-violet` (restaurar el morado original, gratis) nunca pasa por `/purchase`: es un reset puramente local, igual que antes. Cuál tema está *activo* ahora mismo (`U.theme`) también sigue siendo una preferencia local no sincronizada — el servidor solo rastrea qué temas se poseen, no cuál está aplicado; en un dispositivo nuevo el acento vuelve al morado por defecto aunque el tema comprado siga apareciendo como "Adquirido".
- ✅ Suscripciones/Pro conectado (este bloque): `Plan`/`Subscription` ya existían en el schema (sembrados desde el arranque del backend) pero sin módulo/endpoints — se agregó `SubscriptionsModule` (`POST /subscriptions/checkout`, `POST /subscriptions/cancel`) y `Subscription.userId` pasó a `@unique` (una fila por usuario, no historial). `U.pro` deja de ser una bandera de `localStorage`: ahora `learning.service.ts` consulta la suscripción real para decidir vidas infinitas y XP x2 en cada respuesta. Bug real encontrado y corregido: el cliente solo sincronizaba `U.hearts` con el valor real del servidor cuando `U.pro` era `false` — un usuario "Pro" (falso, local) seguía perdiendo vidas de verdad en Postgres sin verlo, hasta que Pro se desactivaba o entraba desde un dispositivo nuevo y aparecía con vidas agotadas sin aviso. El cobro sigue simulado a propósito (sin integrar Stripe real) — decisión explícita, no pendiente.
- ✅ Recarga de vidas con gemas conectada (este bloque): `useGemsHearts()` era el último punto de todo Kodo que seguía mutando `U.gems`/`U.hearts` 100% en el cliente sin llamar al servidor (encontrado al auditar el bloque de Suscripciones/Pro, arreglado en un bloque aparte). Ahora pasa por `POST /learning/hearts/refill`, con el mismo rigor de atomicidad/anti-doble-cobro que Shop y Suscripciones. Con esto, gemas y vidas quedan 100% bajo autoridad del servidor en todos los caminos del frontend — no queda ningún lugar que las modifique localmente sin pasar por la API.
- ✅ Hallazgo crítico de un audit de seguridad server-authority cerrado (este bloque): `GET /lessons/:key` no tenía ningún control de progresión y filtraba la respuesta correcta directamente (`ExerciseOption.isCorrect`, `content.acc`/`ans`/`w`) — combinado con que `POST /learning/exercises/:exerciseId/answer` tampoco verificaba si la lección estaba desbloqueada, cualquier usuario autenticado podía scriptear el currículo completo y farmear XP real (contado en el ranking) sin respetar el orden. Confirmado en vivo contra Postgres durante el audit. Arreglado en dos frentes: `assertLessonUnlocked()` (extraído de `completeLesson()`) ahora también protege `answerExercise()` — 403 sin efectos secundarios si la lección anterior no está completada, sin importar `U.done`/`U.pro` del cliente — y `lessons.service.ts` deja de mandar la respuesta correcta por adelantado; el cliente la recibe recién en la respuesta real de `/answer` (`correctIndex`/`correctAnswer`) para poder seguir mostrando "Respuesta correcta: X" después de un intento. TRANSLATE/ORDER comparten un banco de palabras tap-to-build cuyo orden ERA la respuesta — ahora llega pre-mezclado desde el servidor (`content.bank`). Verificado con una batería nueva de 28 casos más las 6 baterías existentes re-ejecutadas limpias (51+19+29+58+32+22, cero regresiones reales).
- 🔴 Production Readiness — Security Audit realizado (hallazgo crítico identificado, mitigación desplegada; el resto de hallazgos ALTO/MEDIO/BAJO siguen pendientes de cierre): `run-student-code.ts` ejecuta código de ejercicios `RUN` con el módulo `vm` de Node dentro del mismo proceso del API — no es un sandbox real, el propio archivo ya lo documentaba. Mitigación inmediata desplegada: `RUN_EXECUTION_ENABLED` (env, default `true`) bloquea con `503` cualquier ejercicio `RUN` antes de llegar a `runStudentCode()`, sin efectos secundarios, cuando está en `false`. Solución definitiva (pendiente, requiere su propio bloque, ver `apps/api/src/execution/`): Execution Worker separado del proceso NestJS, ejecutando en contenedor Docker efímero real (sin red, filesystem temporal, límites de CPU/RAM/procesos, sin acceso a secretos) — construido y con las guardas de concurrencia/rate-limit ya escritas (código en el repo, gateado por el kill-switch), pero **sin verificar contra un daemon Docker real todavía** (bloqueado por un problema de entorno en la máquina de desarrollo, no del código) — no se activa en producción hasta pasar por esa verificación end-to-end; `RUN_EXECUTION_ENABLED=false` sigue siendo el estado seguro de producción mientras tanto. El contrato `código → ejecución → resultado → grading → XP/progreso` se mantiene exactamente igual, solo cambia DÓNDE ocurre la ejecución.

- ✅ Production Readiness — hallazgos no-Docker cerrados (este bloque): ningún cambio de forma en los endpoints existentes, es endurecimiento de infraestructura. (1) Helmet con `crossOriginResourcePolicy:'cross-origin'` (el frontend es intencionalmente cross-origin). (2) `trust proxy` configurable vía `TRUST_PROXY` (nunca `true`, evita spoofing de `X-Forwarded-For` contra el rate limiting por IP). (3) Validación de variables de entorno al boot (`class-validator` sobre `EnvironmentVariables`) — falla rápido con un error claro si falta `DATABASE_URL` o `JWT_ACCESS_SECRET` es muy corto, en vez de fallar más tarde de forma confusa. (4) Login timing-safe: se compara contra un hash dummy (`DUMMY_PASSWORD_HASH`) incluso cuando el email no existe, para que un email inexistente y una contraseña incorrecta tomen tiempos de respuesta comparables (antes era un canal lateral de enumeración de usuarios pese al mensaje genérico). (5) Rate limit de login endurecido de 10/60s a 8/900s (login sigue devolviendo el mismo `401 Credenciales inválidas.` — solo cambia cuándo empieza a devolver `429`). (6) Logging estructurado: `AllExceptionsFilter` (global, `apps/api/src/common/filters/`) captura toda excepción — HttpException o no — y emite una línea JSON por error (`timestamp/level/method/path/statusCode/message/userId`), nunca el body de la petición ni el stack al cliente; el stack solo va al log del servidor en errores 5xx. La forma de la respuesta de error al cliente sigue siendo `{statusCode, message}`, sin cambios. (7) Reuso de refresh token detectado: si un `refreshToken` ya rotado (revocado) se reenvía, se interpreta como señal de robo y se revocan TODAS las demás sesiones activas del usuario, no solo la petición actual — mismo `401 Sesión inválida o expirada.` de siempre, sin cambio de forma. (8) Límite explícito de tamaño de body: `100kb` en JSON/urlencoded (antes implícito/sin límite explícito) — cualquier petición que lo exceda devuelve `413` en vez de colgar el proceso o depender del default de la librería.
